# methods

## 6. 03 方法：通过具体场景了解怎样判断

方法访谈按“提炼候选 → 用案例校准 → 检查是否充分”循环推进。方法、基础案例和举一反三案例都不设固定总数：简单任务少问，复杂任务按真实缺口增加，不能为了凑数继续问。决策优先级、信息取舍、调整机制与边界判断作为覆盖维度，融入实际场景。

进入方法阶段时告诉创作者：“我们先从你的具体做法聊起，复杂的地方再补案例；你觉得够了，随时说‘先到这里’，我会整理已有内容并标出待补。”这不是每轮重复征求继续许可。动态目标和收口记录见 [方法访谈协议](methods-protocol.md)。

### 6.1 方法候选

从已确认的 01/02 按当前任务提出不重复、有来源的判断假设，尽量写成“当……时，优先……；除非……”。一次展示一个，创作者可认可、改写或拒绝。

| 创作者反馈 | 下一动作 | 能否收敛当前候选 |
| --- | --- | --- |
| “符合我的做法”且对象明确 | 保存对该规则的认可及原话 | 可以 |
| 提供前提、例外或明确替代做法 | 按原意修订；新内容若只是忠实整理，不再重复索要应用许可 | 可以；模型额外推导仍需校准 |
| “这完全不是我的方法”，未给替代 | 标记拒绝，保留原话 | 可以，转下一候选 |
| “不太对”，未说明哪里 | 只问差异：“这条判断里，哪一点和你的做法不一样？” | 不可以，缺少可执行修正 |
| “为什么这么理解” | 解释所依据的来源及假设性质 | 不认可、不拒绝，保留当前位置 |
| “不知道”“先放着” | 保留未决，可看其他候选 | 不能算 accepted |

本案例所依据的方法获认可后，就可以用场景验证，不必等其他独立候选全部处理。后续案例揭示新方法时可继续登记、逐条校准。全部被拒时，从创作者的一次真实处理经历重新提炼；如果仍没有做法，不制造 accepted 规则来推进。

### 6.2 按需选择基础场景

场景只描述“谁、发生了什么、提出什么需求”，先不提供 AI 处理答案。人物服从 01 的目标用户。AI 构造的情境须标明是校准情境，不能写成创作者真实发生过的案例。

尽量让同一个用户的经历连续下去，用刚才的实际回答引出受阻或边界情况，不每问都另编一个人和一套背景。专家讲真实案例时直接问实际处理，如“你当时怎么回她的？”；只有取舍含义确实需要核对时才先说明理解。场景具体后不再叠加辅助例子。需要改动条件时明确说明是假设及改了哪一点；按最能验证当前缺口的顺序推进，不在基础场景首问里给专家预选做法。“责任边缘”等名称供内部覆盖判断，不逐题念给专家。

| 可选观察角度 | 要了解的判断 | 什么回答已够用 | 还缺关键内容时怎样问 |
| --- | --- | --- | --- |
| 初次求助 | 面对信息不完整的求助，先判断什么再行动 | 从当前回答与已确认材料可提取关键判断、下一步及理由 | 真实经历问“你当时怎么回她的？”，假设场景问“你先怎么回她？”；仅缺输入时补“给建议之前，你还得先弄清哪件事？” |
| 行动受阻 | 理想方案做不到时，保留什么、调整什么 | 能明确本情境里的取舍或调整，以及依据 | 带入当前实际限制后问“你会把这套做法简化成什么样？” |
| 责任边缘 | 仍可帮助到哪里，什么条件下要停止 | 是否继续、可处理的范围或停止条件、判断依据 | 带入具体求助后问“她追着问你该怎么办，你会怎么回她？”；已有回答则只补尚缺的范围或停止条件 |
| 明确越界 | 明确不在职责内的要求怎样处理 | 明确不继续承担什么，并能说明与既有边界的关系 | 说明具体越界要求后问“你会怎么跟她说？”；不让专家复述抽象责任定义 |

“关键判断、动作与理由”可以来自已经确认的规则，不要求创作者每题都重复。若回答只是“看情况”“因人而异”，尚不能确定实际做法；只追其中真正影响下一步的一点。这里不要求设计收费、周期交付或完整转交流程。

创作者对具体场景给出的充分、明确处理意见可作为其场景答案保存，保留原话。模型整理加入了原话没有的条件或推论时，新增部分必须另行校准。仅输入非空文字、说“为什么”或“我不知道”，不能自动把场景标为 confirmed。

上表是观察角度，不是四道必问题。一个案例可以覆盖多个维度；已确认材料足够就复用。场景不适用时换一个符合真实任务的场景；维度本身不适用则记录具体理由和依据，不强造故事。新增 M/E 编号须说明与已有案例不同的关键缺口，不能给同一问题换编号规避次数限制。

### 6.3 按需举一反三

对应基础场景有效确认后，按尚未验证的迁移能力构造拓展：例如现实约束变化、原则冲突、边界或风险变化。不限于三个，也不要求每类各一道；每个只改变一个关键条件，其他背景保持一致。已有确认已覆盖迁移判断时，不再重复出题。

这时展示一份根据已确认规则推导的“可能处理方式”，让创作者能判断具体执行是否合理，不能只列原则或写“从可控制的操作中选一项”。先读取对应基础案例及已确认依据的正文；已有的具体做法要保留下来，不把它们概括掉后再让创作者重新提供。

处理方式通常写成 2—4 个短步骤，按本场景需要覆盖：

- **第一步怎么开始**：谁在什么时点，使用什么已有信息，对哪个对象做什么。确实缺关键输入时说清要取得哪一项，不笼统写“了解情况”。
- **具体怎么执行**：给一个当前约束下能实施的操作，交代顺序或示范一句实际说法。例如“把这周的一项真实进展写成‘做了什么／结果是什么’两行”，而不是“优化表达”。
- **做不到时怎么调整**：按已知限制提出替代动作或停止条件，不假设原本不具备的资源突然可用。条件分支用“如果”表达，不把假设写成新发生的事实。
- **怎样知道是否落实**：观察实际行动或产物，如是否完成一顿尝试、是否留下两行记录；后续调整依据是什么。执行完成不能偷换成健康、收入或其他效果已经改善，也不能凭空增加提醒、自动追踪或定期服务承诺。

这是写作时的检查项，不是要求创作者回答四道题。已有依据够用就直接整理；简单案例可以少于四步，不能为凑完整结构编造用量、频次、渠道、能力或结果。构造拓展情境仍只改变一个关键条件；不得为了让方案好做而同时换商家、作息或设备。

正文先用日常说法说明这是根据已有方法推出来的建议，再展示具体动作，最后只问一个确认问题。通常用 180—320 字把场景和做法讲清，简单案例可更短，必要时可展开；这是写作参考，不是字数门槛。宿主使用 `delivery.mode: booklet`，并以 `confirmationObjectIds` 绑定当前场景；不把多项执行步骤写成多个采访问题。场景 markdown 保存同一份具体做法，之后的方法手册也保留关键操作，而不是只在对话里举例、入册时又缩回原则。

**同一约束下的表达示例**

假设创作者在基础案例中已经提出“浓汤、酱料不拌饭”和“夹菜时先沥去表面的油汁”，拓展时仅新增“办公室不能存放自备食物”。可展示：

> 办公室不能存放食物，其他外卖限制保持不变。我会先取消自备食物这一步，沿用你已经提过的操作：
>
> 1. 下一餐先试“浓汤、酱料不拌饭”，从一个明确动作开始。
> 2. 如果餐品已经拌好，就改试“夹菜时先沥去表面的油汁”，不要求商家配合改单。
> 3. 这餐后让用户说清“做到了”或“卡在哪一步”，再决定保留哪个动作、怎样调整。
>
> 我按你前面说的做法，试着排了这个安排。你看，这样处理合不合适？

这个示例说明怎样保留已有具体动作，不是通用饮食方案或效果结论；其他项目应使用它自己的真实依据。模型新增的执行顺序、分支和观察方式仍需创作者校准，不能写成已经确认的经验。

- 明确认可对应处理方式：确认这一场景。
- 提供明确修改：更新对应条件或动作；不顺势重写其他方法。
- 仅否定、提问、不确定：解释或追问一个缺口，不算确认。
- 与既有规则冲突：引用相关两处表达，问清是否存在适用条件或例外；不能自行决定哪条作废。

同一缺口最多三次回答；同一案例累计四次后整理，仅关键缺口且最新回答有实质新增才延长到最多六次。换条件、换措辞和切换案例后回来都不重置该目标计数；连续两次没有新增提前停止。达到任一边界后保留具体待补，可以处理其他独立场景，不要求逐个补齐无关的执行细节。不能把次数耗尽等同于充分，也不能持续新增相似案例来无限延长。


### 6.4 何时停止

每校准一个方法或案例，就检查已有材料是否足以支持当前搭子的实际任务：

- 判断：关键输入、优先级、条件与例外能否指导取舍。
- 行动：能否说清下一步、顺序、理由和可观察的反馈。
- 调整：重要限制变化、执行受阻或原则冲突时，能否合理迁移。
- 边界：适用范围、停止条件和无法处理的情况是否明确。

这些是 Agent 的检查角度，不是追加给用户的四道题。每个判断引用已确认内容；不适用的角度说明理由。缺口会改变实际做法才值得追加案例，只有措辞、装饰细节或重复证明就收口。复杂任务可覆盖多条方法和多个任务分支；不要先固定一长串题目再要求逐个答完。

两种结束方式必须区分：

1. **Agent 判断充分**：简要说明已覆盖哪些关键判断，以及为什么继续问的新增价值已很低；登记 sufficient，直接整理五章并展示待确认版本。仍有待校准目标、冲突或关键缺口就不能写充分。
2. **创作者主动结束**：“先到这里”“够了，整理吧”等明确结束意愿立即生效。不追加“最后一个案例”，不要求解释理由。登记 user_stopped，保留全部未验证目标和缺口，生成有范围说明的五章供确认。叫停不等于认可未展示内容，也不自动确认整册。仅采用已确认内容，不把待补当作搭子已经具备的能力。

用户只想暂停整项创作时沿用 paused；只跳过某个问题不等于结束整个方法阶段。含糊的“差不多”按上下文判断，不能无证据推断叫停。已收口后，只有用户主动提出续谈才恢复；保留历史问题、证据和次数。后续开发严格遵守本版范围，不能把未验证的推导实现为已获认可的方法。
