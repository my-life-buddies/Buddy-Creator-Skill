# 自适应方法访谈协议

进入方法阶段时读取本文件及 methods.md。宿主负责判断语义与覆盖，程序校验依据、版本、结束意愿记录和确认关系。不能从达到某个数量推断充分。

## 目标登记

在 `turn_finish.patch.methods.register` 提交数组，每项严格使用：

- `id`：候选 H01、H02…；基础案例 M01、M02…；拓展案例 E01、E02…。超过九个继续 H10/M10/E10；不设总数量门槛。
- `title`：本次实际校准的判断或案例名称。
- `purpose`：当前尚未验证的具体判断，以及为什么值得新增一个独立目标。不能只写“再举一例”。
- `evidence`：已有真实输入、已读资料或产物的 Ref 数组，格式与 host-guide 相同。

首次登记后该目标的名称和目的保持稳定。修订同一目标的产物，沿用原 ID；不能换编号、同义改写目的来重置次数。新目标有独立的判断条件或任务分支时才新增，一次无需预登记所有可能场景。单缺口三次、案例四次整理/最多六次、连续两次无新增的规则继续生效。

候选产物为 hypothesis.H1、H2…（对应目标 H01、H02…）；场景产物为 scenario.M01… / E01…。先登记再保存产物或提问，可以在同一轮操作。新案例 dependencies 除各上游阶段已确认章节外，还须包含实际依赖的 accepted 方法；拓展须包含对应已确认 M 案例。新方法可以在后续案例揭示缺口时补入，不必一次确定全部。

新作品默认使用此协议。没有 `state.methodInterview.version=1` 的旧作品在未完成的方法阶段首次提交 methods 补丁时接入：保留已存在产物、已采访目标、原话、计数和确认；未使用的旧固定题目不自动成为必答项。已经整册确认的方法手册不会因升级被重开。尚未完成的旧册若已有部分章节确认，接入时这些章节需重新绑定本次收口并展示，方法和案例本身的有效确认保留。

## 有依据地结束

`patch.methods.conclude` 严格包含 `status、summary、coverage、unresolved、evidence`：

**Agent 判断充分**：

- status：`sufficient`。
- summary：对创作者说明已覆盖的范围及收口理由。
- coverage：四个键 `decisions、actions、adaptation、boundaries`。每项包含 `status: covered 或 not_applicable`、具体 `reason`、引用已确认产物的 `evidence`。
- unresolved：`[]`。仍有未校准目标或关键缺口不能提交充分。
- evidence：支持整体判断的真实 Ref 数组。

一个案例可以支持多个维度，已确认定义或知识也可说明某个维度不适用。至少需要一个实际认可的方法和一个经用户校准的基础案例；不是要求四个独立案例。拓展数量由尚未验证的迁移能力决定。程序不能代替宿主判断证据的含义。

**创作者主动结束方法访谈**：

- status：`user_stopped`。
- summary：说明用户要求先结束、本版采用哪些已确认内容。
- coverage：`{}`，叫停不能写成覆盖充分。
- unresolved：实际已知的其他范围限制；程序还会自动汇总未校准目标、未决项和缺口，不能清空它们假装完成。
- evidence：必须精确引用本轮明确结束意愿。使用 `intent: revision`，不把叫停当成场景回答，不提交 interview.assessment。

“不知道”“先跳过这个”不一定是结束整个方法阶段，依据上下文区分。暂停整个创作仍使用 paused，不代替方法叫停。不得通过关键词自动判定同意或代替用户叫停。

收口可以和最后一个案例的真实确认、五章生成放在同一轮：程序先处理确认和案例，再保存收口，再生成章节。也可以先用只有 text 的 delivery 说明已收口，保留状态后整理；收口后的有效下一步是展示五章，不继续采访。不要遗留一个要求用户回答的旧问题。

## 有限范围的手册仍需确认

五章固定结构不变；程序将本次收口绑定在 `data.methodConclusion` 中。用户叫停时，程序把未验证范围写进每章正文和 unresolved，出现在预览及最终导出中。只使用已确认的方法和案例作为结论依据；尚未验证的内容放入待补，不能作为搭子能力或承诺。

收口后须展示当前五章实际版本，通过 `confirmationScope: booklet` 取得新的整册确认。用户的叫停不是整册确认，更不是 pending 案例的确认。只有带有效 user_stopped 范围说明的方法章节可以在有待补时确认；其他阶段及单个方法/案例的严格确认规则不变。范围说明变化后必须重新展示。

## 续谈与恢复

用户主动要求续谈时，在 `intent: resume 或 revision` 下提交：

`patch.methods.resume = {reason: 具体续谈内容, evidence: 本轮明确请求的 Ref 数组}`。

续谈归档旧收口依据并使旧方法章节确认失效，保留目标、案例、全部原话和次数。已达到单目标上限时，还需按 interview.reopen 明确恢复对应目标，不能静默清零。仅继续整理或确认收口后的手册不需要 resume。对已完成作品的修订按原有修订流程回到方法阶段后再续谈。

收口绑定上游材料、方法/案例版本、确认和采访缺口。任何相关版本变化都需要重新评估并展示新手册，不能复用旧的“已经充分”。用户主动结束的意愿即使遇到旧依据变化也仍然有效，不自动重新发问。
